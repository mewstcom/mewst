### `go/internal/usecase/send_email_confirmation.go`

**ステータス**: 要修正

**チェックしたガイドライン**:

**問題点・改善提案**:

- **[@go/docs/architecture-guide.md#レイヤー間の依存関係]**: UseCase が `templates` を直接 import してテンプレートをレンダリングしている。作業計画書では「application-layer から `templates` deny を削除（メールレンダリングのため許可）」とあり depguard 上は許容されるが、`email.Sender` インターフェースには `Send(ctx, SendInput)` メソッドがあり、`SendInput.HTMLBody` / `TextBody` は `templ.Component` を直接受け取れる。これを使えば UseCase 内でのバッファリング・レンダリングが不要になる。

  現状の UseCase は Worker の `renderEmailTemplates` + `SendRaw` パターンをそのままコピーしているが、Worker を経由しない UseCase では `Send` の方が自然。

  ```go
  // 現在のコード（renderEmailTemplates + SendRaw）
  htmlBody, textBody, err := uc.renderEmailTemplates(ctx, input)
  if err != nil { ... }
  err = uc.sender.SendRaw(ctx, email.SendRawInput{
      To:       input.Email,
      Subject:  subject,
      HTMLBody: htmlBody,
      TextBody: textBody,
  })
  ```

  **修正案**:

  ```go
  // Send を使い、templ.Component を直接渡す
  var htmlBody, textBody templ.Component
  switch input.Locale {
  case "en":
      htmlBody = email_confirmation.EnHTML(input.Email, input.Code)
      textBody = email_confirmation.EnText(input.Email, input.Code)
  default:
      htmlBody = email_confirmation.JaHTML(input.Email, input.Code)
      textBody = email_confirmation.JaText(input.Email, input.Code)
  }

  err := uc.sender.Send(ctx, email.SendInput{
      To:       input.Email,
      Subject:  subject,
      HTMLBody: htmlBody,
      TextBody: textBody,
  })
  ```

  **メリット**:
  - `renderEmailTemplates` メソッド・`bytes` import が不要になり約 25 行削減
  - テンプレートレンダリングのエラーハンドリングは `ResendSender.Send()` に集約される
  - `SendRaw` は Worker 向けの API（コメントにも「Worker用」と記載）であり、UseCase が使うのは設計意図に反する

  **対応方針**:
