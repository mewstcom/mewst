## 概要

<!--
ガイドライン:
- この機能が現在「どのように動いているか」を簡潔に説明

Go 版では、chi ルーターにマッチしないパスへのアクセス時（404）と、リバースプロキシで Rails 版への接続エラー発生時（502）に、アプリケーションのデザインに沿ったスタイル付きエラーページを表示する。エラーページは templ テンプレートで実装されており、日本語・英語の両方に対応している。

**目的**:

- ユーザーが存在しないページにアクセスした際や、Rails 版への接続エラーが発生した際に、統一されたデザインのエラーページを表示してユーザー体験を改善する
- エラーページ系テンプレートを一箇所に集約し、保守性を向上させる

**背景**:

- エラーページはセッション取得や DB アクセスを必要としないスタンドアロン方式を採用している。エラー発生時にセッションや DB が利用できない可能性があるため、外部依存のないスタンドアロン設計とすることで、エラーページ自体の表示を確実にしている
- Rails 版の `public/404.html` のデザイン・トーンを踏襲し、Go 版と Rails 版で統一感を持たせている

## 仕様

### 404 エラーページ

- chi ルーターにマッチしないパスにアクセスすると、HTTP 404 ステータスコードとともにスタイル付きの 404 エラーページが表示される
- エラーページには絵文字（🫥）による視覚的なインジケーター、エラーメッセージ、「ホームに戻る」リンクが含まれる
- ユーザーの Accept-Language ヘッダーに基づいて日本語または英語で表示される

### 502 エラーページ

- リバースプロキシで Rails 版への接続に失敗した場合、HTTP 502 ステータスコードとともにスタイル付きの 502 エラーページが表示される
- エラーページには絵文字（⚠️）による視覚的なインジケーター、エラーメッセージ、サブメッセージ（「しばらくしてから再度お試しください。」）、「ホームに戻る」リンクが含まれる
- ユーザーの Accept-Language ヘッダーに基づいて日本語または英語で表示される

### 共通仕様

- エラーページの表示にセッション取得や DB アクセスは不要（スタンドアロン方式）
- CSS はインライン埋め込みで外部依存なし
- 各エラーページは画面中央（上部 55% の位置）に配置される

### ファイル構成

```
go/internal/templates/pages/errors/
├── not_found.templ          # 404エラーページテンプレート
└── bad_gateway.templ        # 502エラーページテンプレート

go/internal/handler/
└── errors.go                # NotFound / BadGateway ヘルパー関数
```

### テンプレート設計

エラーページはレイアウトに依存しないスタンドアロンの templ コンポーネントとして実装している。各テンプレートは完全な HTML ドキュメント（`<!DOCTYPE html>` から `</html>` まで）を出力する。

**共通のデザイン要素**:

- 絵文字による視覚的なインジケーター（404: 🫥、502: ⚠️）
- i18n 対応のエラーメッセージ
- 「ホームに戻る」リンク（`/` へのリンク）
- CSS はインライン埋め込み（外部依存なし）
- システムフォントスタック、レスポンシブ対応

### ヘルパー関数

`internal/handler/errors.go` に 2 つのヘルパー関数を提供している。

- **`handler.NotFound(w, r)`**: HTTP リクエストから言語を検出し、ロケールを設定した上で 404 テンプレートをレンダリングする
- **`handler.BadGateway(w, r)`**: 同様に 502 テンプレートをレンダリングする

### chi ルーターの設定

`cmd/server/main.go` で `r.NotFound(handler.NotFound)` を登録し、ルーティングにマッチしなかった場合にスタイル付きの 404 ページを表示する。

### リバースプロキシでの使用

`internal/middleware/reverse_proxy.go` のエラーハンドラー内で `errors.BadGateway().Render(ctx, w)` を呼び出し、Rails 版への接続エラー時に 502 ページを表示する。

### i18n 翻訳キー

404 ページ用に 3 キー、502 ページ用に 4 キーの翻訳を `ja.toml` / `en.toml` に定義している。

**404 ページ**:

| キー                           | 日本語                                | 英語                                            |
| ------------------------------ | ------------------------------------- | ----------------------------------------------- |
| `error_not_found_title`        | ページが見つかりませんでした \| Mewst | Page not found \| Mewst                         |
| `error_not_found_message`      | お探しのページは見つかりませんでした  | The page you are looking for could not be found |
| `error_not_found_back_to_home` | ホームに戻る                          | Back to home                                    |

**502 ページ**:

| キー                             | 日本語                                             | 英語                                            |
| -------------------------------- | -------------------------------------------------- | ----------------------------------------------- |
| `error_bad_gateway_title`        | サービス接続エラー \| Mewst                        | Service Connection Error \| Mewst               |
| `error_bad_gateway_message`      | 申し訳ございません。現在サービスに接続できません。 | Sorry, we are unable to connect to the service. |
| `error_bad_gateway_submessage`   | しばらくしてから再度お試しください。               | Please try again later.                         |
| `error_bad_gateway_back_to_home` | ホームに戻る                                       | Back to home                                    |

## 採用しなかった方針

<!--

- 将来の開発者が同じ検討を繰り返さないための判断記録として活用する
- 後から実装された場合は、該当項目を削除する

### デフォルトレイアウト内でエラーページを表示する方針

サイドバーやナビゲーションを含むデフォルトレイアウトを使ってエラーページを表示する方針を検討した。404 発生時にセッション情報やサイドバーデータの取得が必要になり追加の DB アクセスが発生すること、セッションや DB が利用できない場合にエラーページ自体が表示できなくなるリスクがあることから不採用とした。

### ResponseWriter をラップするミドルウェアでレスポンスを書き換える方針

`http.NotFound` をそのまま使い、ミドルウェアでステータスコード 404 のレスポンスをインターセプトしてエラーページに差し替える方針を検討した。`ResponseWriter` のラップは実装が複雑になること（`WriteHeader` と `Write` の順序制御、`Flush` や `Hijack` インターフェースの対応など）、ヘルパー関数で直接レンダリングする方がシンプルで明示的であることから不採用とした。

### 502 ページを既存のハードコード HTML のまま残す方針

`render502ErrorHTML()` 関数の Go 文字列リテラルによる HTML を変更せず、404 のみ templ テンプレート化する方針を検討した。エラーページ系のテンプレートが分散すること、i18n 対応が困難であることから、templ テンプレートに統一して保守性を向上させる方針を採用した。
