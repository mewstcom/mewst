## 設計改善の提案

### `go/internal/handler/errors.go`: NotFound と BadGateway の Content-Type ヘッダー設定の不一致

**ステータス**: 要確認

**現状**:

`BadGateway` は `Content-Type` ヘッダーを明示的に設定しているが、`NotFound`（error-1-1 で実装済み）は設定していない。

```go
// NotFound - Content-Typeを設定していない
func NotFound(w http.ResponseWriter, r *http.Request) {
    // ...
    w.WriteHeader(http.StatusNotFound)
    // ...
}

// BadGateway - Content-Typeを明示的に設定している
func BadGateway(w http.ResponseWriter, r *http.Request) {
    // ...
    w.Header().Set("Content-Type", "text/html; charset=utf-8")
    w.WriteHeader(http.StatusBadGateway)
    // ...
}
```

**提案**:

`NotFound` にも `Content-Type` ヘッダーの設定を追加して一貫性を持たせる。Go の `net/http` はコンテンツスニッフィングで自動検出するため機能上の問題はないが、明示的に設定する方が堅牢。

```go
func NotFound(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()
    locale := i18n.DetectLanguage(r)
    ctx = templates.WithLocale(ctx, locale)
    w.Header().Set("Content-Type", "text/html; charset=utf-8")
    w.WriteHeader(http.StatusNotFound)
    if err := errors.NotFound().Render(ctx, w); err != nil {
        slog.ErrorContext(ctx, "404ページのレンダリングに失敗", "error", err)
    }
}
```

**メリット**:

- エラーヘルパー関数間の一貫性が向上する
- Content-Type の自動検出に依存しない堅牢な実装になる

**トレードオフ**:

- error-1-1 ブランチの変更に遡及する必要がある（このブランチで対応可能）
- 機能上は現状でも問題ない（Go が自動検出する）
